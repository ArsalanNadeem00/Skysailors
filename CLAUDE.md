## Project overview

`ShipGame` is an Unreal Engine **5.7** C++ project (not a git repository). It started from Epic's standard Third Person template — `DefaultGame.ini` still calls it "Third Person Game Template" and the source tree carries the template's original variant sample content (`Variant_Combat`, `Variant_Platforming`, `Variant_SideScrolling`) largely unmodified. The actual game being built on top of that scaffolding is a multiplayer **ship** game: players spawn aboard a moving ship (`AShipActor`), can walk around on its deck (it's a moving platform via `UCharacterMovementComponent`'s standard support), and one player at a time can take the helm (`ASteeringWheel`) to steer it. Despite starting from the third person template, player characters now use the first person character and setup.

## Architecture

### Module layout

Single primary game module `ShipGame` (`Source/ShipGame/ShipGame.Build.cs`), with public dependencies on `Core`, `CoreUObject`, `Engine`, `InputCore`, `EnhancedInput`, `AIModule`, `StateTreeModule`, `GameplayStateTreeModule`, `UMG`, `Slate`, `Niagara`, and a private dependency on `SlateCore` (needed for `FReply`, used by `UShipToolMenuWidget`'s key handling). Two build targets: `ShipGame` (Game) and `ShipGameEditor` (Editor), both `Unreal5_7` include-order.

The default game mode is set via `Config/DefaultEngine.ini` (`GlobalDefaultGameMode=/Game/Blueprints/BP_ShipGameMode`), and the startup/default map is `Content/ThirdPerson/Lvl_ThirdPerson`. Most gameplay classes are C++ base classes (many marked `abstract`) with a matching Blueprint subclass in `Content/Blueprints/` (e.g. `AShipActor` → `BP_ShipActor`, `AShipGameMode` → `BP_ShipGameMode`) that fills in meshes, input assets, and per-instance tuning. When investigating gameplay behavior, always check whether the relevant Blueprint overrides a C++ default — the C++ headers document intent extensively in comments, but numeric defaults and asset references are often only real in the Blueprint.

### Ship game (the actual game — `Source/ShipGame/*.h/.cpp` at the top level)

- **`AShipActor`** (`ShipActor.h`) — the ship itself. Moves forward at a constant `ForwardSpeed`; helm input only ever affects yaw/vertical, never throttle. Deliberately **does not** rely on Unreal's built-in actor transform replication (`bReplicateMovement = false`) because that produces visible jitter/teleporting for a non-physics actor with characters standing on it. Instead every machine (server and clients) runs the same `MoveShip()` integration each tick from a small set of replicated helm-input fields (`bHelmControlled`, `HelmYawInput`, `HelmVerticalInput`), and the server separately replicates its authoritative transform (`ServerLocation`/`ServerRotation`) purely so clients can gently drift-correct (`CorrectDriftFromServer`) toward it without snapping. This pattern (locally-simulated motion + replicated inputs + separate soft drift-correction) is the key architectural idea in this file — read the class-level comment in `ShipActor.h` before changing anything about how the ship moves or replicates. The root component is `HazardBox` (a `UBoxComponent`) rather than the visible mesh, specifically so it has something to sweep for collision each tick; everything else (hull mesh, spawn points, deck props, `UShipBreakComponent`s) is attached beneath it and rides along for free. Also owns the hull-damage model: `HullIntegrity` drops by `HullDamagePerCrash` (cooldown-gated) whenever `HazardBox` hits something tagged `"crash"`, which also plays a camera shake/knockback and, at 0, plays a "ship destroyed" fade/quit sequence — and accumulates into `DamageSinceLastShipBreakActivation`, activating one random inactive `UShipBreakComponent` every `DamagePerShipBreakActivation` (see below). `RepairHull` (called by the wrench, see `AShipCharacter`) restores it.
- **`ASteeringWheel`** (`SteeringWheel.h`) — a stationary interactable `Pawn` on deck. A character interacts with it to have their `PlayerController` possess it (`TryEngage`, server-only, enforces single-occupant); while possessed it feeds A/D → `AShipActor::SetHelmYawInput` and W/S → `SetHelmVerticalInput`. Releasing it (interact again or disconnect) hands control back to the previous pawn.
- **`AShipCharacter`** (`ShipCharacter.h`) — the player pawn, Enhanced Input based (Move/Look/Jump/Interact/SwingAction/ToolUseAction actions bound via `AShipGamePlayerController`'s mapping contexts, not on the character itself). `Interact()` engages the nearest unoccupied `ASteeringWheel` in range, or else opens `UShipToolMenuWidget` at the nearest `AClosetDoor` — always via a server RPC (`ServerInteract`) so the range/facing check is authoritative. Also carries the tool system: `EquippedTool` (`EEquippedTool::Mop`/`Wrench`/`None`, chosen via the closet's menu) plus a `TMap<EEquippedTool, FToolDefinition>` (`ToolDefinitions`, filled in the Blueprint) drives a generic swing action and a per-tool "tool-use action" effect (mop destroys the nearest `APuddle`, wrench repairs+deactivates the nearest active `UShipBreakComponent`). **Gotcha:** the character uses third-person-style movement-oriented rotation (`bOrientRotationToMovement = true`, `bUseControllerRotationYaw = false`) with a first-person camera decoupled from the capsule (`bUsePawnControlRotation` on the camera) — so `GetActorForwardVector()` tracks movement direction, not view direction, and does *not* reflect where a stationary/strafing player is looking. All the `FindNearest*` interaction facing checks therefore go through `GetInteractionFacingDirection()` (controller view yaw), not the actor's forward vector — keep using that helper (or extend it) for any new facing-gated interaction rather than reaching for `GetActorForwardVector()` directly.
- **`AClosetDoor`** (`ClosetDoor.h`) — stationary interactable with no state of its own; interacting opens `UShipToolMenuWidget` (`ShipToolMenuWidget.h`, abstract UMG base — buttons live in a Blueprint subclass, each calling `OwningCharacter->RequestEquipTool(NewTool)`). While the menu is open, input is switched to `FInputModeUIOnly` (mouse shown, character's Enhanced Input silenced); the widget's own `NativeOnKeyDown` closes it again on Escape or on whatever key is currently bound to `InteractAction` (queried live via `UEnhancedInputLocalPlayerSubsystem::QueryKeysMappedToAction`, not hardcoded).
- **`APuddle`** / **`ARainZone`** (`Puddle.h`, `RainZone.h`) — weather/hazard pair: `ARainZone` is a level-placed trigger that, while the ship's `HazardBox` is inside it, plays a rain Niagara effect and periodically rolls a chance to spawn an `APuddle` at a random point on `AShipActor::DeckArea`. Puddles slip any character that walks into `SlipTriggerSphere` (`AShipCharacter::TrySlip`) and are destroyed by the mop's tool-use action.
- **`UShipBreakComponent`** (`ShipBreakComponent.h`) — a `UNiagaraComponent` subclass placed *directly* on `AShipActor`/`BP_ShipActor` (one instance per hazard spot, positioned individually in the Blueprint's Components panel) rather than as a separate actor, so it's always attached and always rides the ship — no runtime `AttachToComponent` needed, unlike the other deck actors above. Starts inactive (invisible, `bAutoActivate = false`, not interactable); `AShipActor::ActivateRandomShipBreak` turns one on at a time as hull damage accumulates (see above). `SetBroken(false)` (called by the wrench fix, not `Destroy()`) turns it back off so the same spot can break again later. `bIsBroken` is a genuinely **replicated** property — unlike most cosmetic/one-shot state in this codebase, which uses "server decides, everyone plays it" `NetMulticast` RPCs (see `MulticastPlaySwing` etc. below) — specifically because it's persistent ongoing state a client joining mid-match still needs to see.
- **`AShipGameMode`** (`ShipGameMode.h`) — overrides `HandleStartingNewPlayer_Implementation` (instead of the default `PostLogin`/`RestartPlayer` flow) specifically to skip Unreal's default `PlayerStart` lookup and always spawn new players directly on the ship, round-robining through the ship's spawn points.
- **`AShipGamePlayerController`** — applies the `UInputMappingContext`s and (optionally) spawns mobile touch controls; this is the abstract base Blueprinted as `BP_ShipPlayerController`. Also creates/destroys `UHelmHUDWidget` (`HelmHUDWidget.h`, a screen-space hull-integrity bar) exactly while this player possesses an `ASteeringWheel`.

Cosmetic effects/animations throughout `AShipCharacter`/`AShipActor` (swings, tool-use montages, slips, crash shake/knockback, rain) follow one consistent multiplayer pattern: the server validates and calls a `NetMulticast` RPC that every machine (including the server) runs identically, rather than replicating a persistent flag. `UShipBreakComponent::bIsBroken` is the one deliberate exception — see its bullet above for why.

### Non-obvious gotchas worth knowing before touching related code

- **Interaction facing checks must use view direction, not actor rotation.** See the `AShipCharacter` bullet above — `GetActorForwardVector()` lags behind where the player is actually looking whenever they're stationary or strafing, because rotation is movement-oriented, not controller-oriented. Always go through `GetInteractionFacingDirection()`.
- **Niagara effects attached to the ship need "Local Space" enabled per-emitter in the Niagara System asset**, or particles will visibly lag behind/trail during fast motion (most noticeably during `AShipActor`'s crash knockback) — particles simulated in world space keep their spawn-time world position instead of moving with the component. This is a per-Emitter toggle in the Niagara System editor (Emitter Properties → Local Space), not something settable from C++/the component instance — check it on any Niagara System you assign to a ship-attached component (`UShipBreakComponent`, `ARainZone::RainEffect`, etc.).
- **Ship breaks are components, not actors.** They used to be a separate `AShipBreak` actor (auto-attaching itself to the ship in `BeginPlay`, like `AClosetDoor`/`APuddle` still do); that class is gone. Ship breaks are now `UShipBreakComponent` instances added straight into `BP_ShipActor`'s component hierarchy (one per hazard spot, positioned individually) — add new break points there, not as level-placed actors.

### Template variant sample content (`Source/ShipGame/Variant_Combat`, `Variant_Platforming`, `Variant_SideScrolling`)

These three folders are Epic's stock Third Person template variant gameplay samples, included by the template and largely untouched — not part of the ship game's active gameplay loop (the default game mode/map is the ship game, not any of these variants). Each is self-contained:
- **Variant_Combat** — melee combat sample: `ACombatCharacter` (combo/charged attacks, HP, ragdoll death+respawn) implementing `ICombatAttacker`/`ICombatDamageable` interfaces (`Interfaces/`), StateTree-driven AI (`AI/CombatAIController`, `AI/CombatStateTreeUtility`, EQS contexts), and supporting gameplay actors (`Gameplay/CombatDamageableBox`, `CombatLavaFloor`, etc.) plus a UMG life bar (`UI/CombatLifeBar`).
- **Variant_Platforming** — `APlatformingCharacter`/`APlatformingGameMode` with a dash move (`Animation/AnimNotify_EndDash`).
- **Variant_SideScrolling** — 2.5D side-scroller sample: fixed-axis `ASideScrollingCharacter`, `ASideScrollingCameraManager`, StateTree AI NPCs (`AI/`), interactables via `Interfaces/SideScrollingInteractable` (jump pads, moving/soft platforms, pickups in `Gameplay/`), and a UMG HUD (`UI/SideScrollingUI`).

### Content structure

Mirrors the source split: `Content/Blueprints` holds the ship game's Blueprint layer (`BP_ShipActor`, `BP_ShipCharacter`, `BP_ShipGameMode`, `BP_ShipPlayerController`, `BP_SteeringWheel`, `BP_ClosetDoor`, `BP_Puddle`, `BP_FloatingRock`) — `UShipBreakComponent` instances live inside `BP_ShipActor` itself rather than as their own Blueprint asset, and there's no dedicated `BP_RainZone` yet (`ARainZone` can be placed directly). The two UMG widgets live in `Content/UI` instead: `WBP_HelmHUD` (`UHelmHUDWidget` subclass) and `WBP_ShipToolMenu` (`UShipToolMenuWidget` subclass). `Content/Variant_Combat`, `Content/Variant_Platforming`, `Content/Variant_SideScrolling` hold each template sample's assets/Blueprints/anims/input. `Content/ThirdPerson` and `Content/FirstPerson` are template-provided character assets/levels; `Content/Weapons` and `Content/LevelPrototyping` are shared art/prototyping assets. Enhanced Input assets live in `Content/Input` (top-level, shared) plus per-variant `Input/` subfolders.

Networking note: since the ship game is built around multiplayer replication (see `AShipActor` above), when adding new ship-related gameplay state, follow the existing pattern — replicate only the minimal authoritative inputs/state needed, run the actual simulation locally on every machine from those replicated inputs, and use a separate soft drift-correction if you also need to guard against server/client divergence, rather than turning on `bReplicateMovement`/relying on transform replication directly.
